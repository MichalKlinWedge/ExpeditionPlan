# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ExpeditionPlan: AI trip planner. Web **Planner Hub** (`apps/web`, Next.js) for planning, Android app **Expedition Planner** (`apps/mobile`, Expo; called „Pocket Guide” in the spec) for the trip itself, offline-first. Backend: Supabase (Postgres + RLS + Realtime + Storage), web on Vercel. Built by one developer on the experience of FormaSync (`D:\AI\Kardio`).

Read before larger work:
- `SPECYFIKACJA.md` — the spec. §5 is the data model, §7 the schedule/constraint engine, §4 the AI pipeline, §0.2 why the model looks the way it does (it was derived from the user's real plans in `examples/`).
- `PLAN_ETAPOWY.md` — stages (Etap 0 → PoC-0…5 → MVP-1…4 → v1.0). Each stage has an acceptance criterion; work toward it.
- `docs/USLUGI.md` — verified terms/limits of external services. Don't introduce a service it marks NIE (Google Places, MapTiler offline, tile.openstreetmap.org bulk).

All other docs (everything except this file, which is mixed), UI strings and code comments are in **Polish**; identifiers in English.

## Architecture rules

- **Domain logic lives in `packages/core`** and must run identically in the browser, on the phone (offline) and in Supabase Edge Functions (Deno). Keep it pure TS: no Node/Expo/Next imports outside tests.
- Packages are consumed as **TypeScript source** (`main: src/index.ts`), with **explicit `.ts` extensions in relative imports** — required by Deno. `allowImportingTsExtensions` is on everywhere; Next transpiles them via `transpilePackages`.
- **Zod schemas are the single source of truth** for form input, AI output, and `jsonb` columns. jsonb content is camelCase (Zod); table columns are snake_case.
- **Shared labels, formatting, errors:** labels of schema values live in `packages/core/src/labels.ts` (`MEMBER_ROLE` — `owner` shows as „organizator”, `CONTACT_ROLE`, `ITEM_KIND`, `BOOKING_KIND`, `PRICE_BASIS`, `BOOKING_STATUS`, `PAY_WHEN`, `PAY_METHOD`, `BUDGET_LINE_STATUS`, `NOTE_TOPIC`, `SLACK_LABEL`); don't redefine them in the apps. Formatting is in `packages/core/src/format.ts` (`plural`, `pluralForm`, `formatKm`, `dayLabel`, `dayLabelShort`, `dayChip`, `dayMonth`, `shortDate`, `capitalized`) plus `formatMinutes`, `formatMoneyRange`, `moneyToInput`, `fxLine`. A link meant for a human is `HttpUrl` (`schemas/common.ts`, http(s) only). Database errors shown to the user go through `dbErrorMessage` / `dbLoadError` (`packages/sync/src/remote.ts`); web actions load the trip with `pullTrip` and report schema errors with `validationError` (`apps/web/src/lib/trip-snapshot.ts`); `lockedRefs` (`packages/sync/src/document.ts`) lists the refs of `user_locked` items. On the Miejsca and Opisy miejsc pages changes sit behind „Edytuj” (`EditToggle`), as on Posiłki. Deleting a vault file from the bucket is a hard delete on purpose: the document is sensitive (`apps/web/src/components/vault.tsx`); journal files stay.
- Time in plans = **local date/time + IANA zone** (`LocalDateTime` + `TimeZone`), never UTC instants. Real events (expenses, delays) use timestamptz. Money = integer minor units + ISO currency; plan prices use the `Price` schema (ranges, "from", age tiers).
- `packages/planner`: the „Zaplanuj z AI” chain (`planTrip`: stage 1 → day facts → stage 2 chunks → pins → place grounding → ORS travel times when `route` is given), pure TS with injected AI client, place lookup (`geoapifyLookup` in the app, cached Nominatim/Photon in tools) and holidays. Used by the web server action `planWithAi` (Gemini, D8) and by `tools/plan-ai`. The result is a NEW trip „Szkic AI: …” via `import_trip`; the user moves points into the real plan on `/trips/[id]/compare?draft=…`, which `AiPlanButton` opens right after the run (the draft's own plan page only shows a „To szkic AI” banner with links back) (`packages/core/src/plan-merge.ts` + `saveMergeEdit`; copied items are `source: 'ai'`, not `user_locked`). Server keys `GEMINI_API_KEY`, `GEOAPIFY_API_KEY`, `OPENROUTESERVICE_API_KEY` reach `apps/web/.env.local` through `scripts/sync-env.mjs` (no `NEXT_PUBLIC_` prefix → never in the browser).
- `packages/ai`: one client (`createAiClient`) over Claude/Gemini/OpenAI; keys come from config/env (server-side only — never in the browser or APK). Use `askStructured(client, schema, prompt)` for anything that becomes data: it validates with Zod and gets exactly one repair attempt. Model names are never guessed — `listModels()` is the source. With `failover` (the web's Gemini clients) a busy model (503/529/429) gets one retry, then cheap stand-ins from that list (`fallbackModels`: newest stable Flash-Lite, then Flash, never Pro).
- AI produces **drafts and patches, never silent overwrites**; user-edited items are `user_locked`.
- **Propozycje AI** (`/trips/[id]/compare?review=1`, tile on the trip page, card on the compare chooser): `planner/src/review.ts` `reviewPlan` sends the plan with code facts (engine times/warnings, straight-line km from the previous mapped point and `transportBefore`, places off the map, short descriptions) → `PlanReview` = independent suggestions, each a `PatchOp[]` (the `/tune` ops plus `set_leg` and `set_place`; `set_place` only sets `searchName`, Geoapify places it on apply, private places are refused via `skipReason`). Stored in `ai_runs` (stage `review`, `StoredReview` with `applied`/`dismissed`). The page compares the plan with the same plan after all pending patches (same refs, exact new/changed/removed marks, `lib/review-view.ts`); apply/dismiss one or the selected (`app/review-actions.ts`). Saving after any AI patch goes through `lib/patch-save.ts` `savePatchedPlan` (grounding, `saveMergeEdit`, changed places via `saveElements`), shared with `/tune`.
- `packages/sync` (PoC-4): phone ↔ Supabase sync. Every write in a trip bumps `trips.sync_version` and stamps the row's `row_version` (trigger, serialized by the trip row lock); clients pull `row_version > last` via the `pull_changes` RPC (one snapshot). Phone writes (`schedule_events` append-only, `expenses`, `expense_splits`, `settlements`, `packing_checks`, `journal_entries` — `OutboxTable`) go through a SQLite outbox: local row + outbox entry in one transaction, idempotent upsert with client UUIDv7. No hard deletes — `deleted_at`. `LocalDb` is a sync interface (expo-sqlite in the app, `node:sqlite` in tests); the phone keeps server rows generically in one `rows (tbl, id, data)` table.
- **Schema (MVP-1)**: `supabase/migrations/*_mvp1_*.sql` = full §5 model (deviations in SPECYFIKACJA §5 „Odstępstwa w MVP-1”). Every `TripDocument` collection has a table with a `ref` column; common columns, version triggers, `activity_log` and RLS are added by loops in `mvp1_access.sql` — a new trip table goes into those arrays and into `synced_tables()`. `packages/sync/src/document.ts` (`SPECS`) is the only TripDocument ↔ rows mapping; a new document field needs a column there too (round-trip test over the 5 fixtures guards it). Whole documents are written via the `import_trip` RPC (one transaction, deferred FKs). Invites: `create_invite` / `accept_invite` (token hash only). Creating trips requires `app_metadata.trip_creator` (set only with the service key; `can_create_trips()` in RLS) — other accounts only see trips they were invited to; web AI/Geoapify/ORS actions additionally need the e-mail in `AI_ALLOWED_EMAILS`. Single-element writes outside the day plan (AI drafts stage 4/5, logistics editor) go through `saveElements` in `packages/sync/src/plan-save.ts`. After a migration: `npm run gen --workspace packages/db` (types), `npm run test:db` (pgTAP permission matrix).
- **Trip-time data outside `TripDocument`** (rows in `CachedTrip.live`, written via outbox): expenses + splits + settlements (`settle` in core: who owes whom, children to guardian, households), packing checks (shopping list = packing items in category `zakupy`, `core/meals.ts`; `items.self_cooked` marks meals cooked by the group), journal (`journal_entries`, photos in private bucket `journal`, phone queue in `features/trip/journal-photos.ts`; the web adds entries straight from the browser, `components/journal-editor.tsx`; an entry with `item_id` is a photo of a plan item, added and shown on the web item card (section „Zdjęcia” at the end; „odłącz od punktu”; `components/journal-link.tsx` links earlier entries of that day or without a day, author or owner/editor in edit mode) and in phone item details `ItemPhotos`; day and time come from the photo's EXIF, `core/photo-time.ts`, then the item's planned start; order is `taken_at`, so editing, ↑/↓, phone drag by „≡” (`DraggableEntries`, `PanResponder`, the tab's scroll stops while dragging) and moving to another day change it via `core/journal-order.ts`, no separate order column; removing a photo only clears `photo_path`). Receipt from a photo: phone `lib/web-api.ts` → web `POST /api/receipt` (Bearer session token, `AI_ALLOWED_EMAILS`, Gemini via `planner/src/receipt.ts`) → draft that fills the expense form. Task reminders: `DocTask.remindAt` (`tasks.remind_at` jsonb `{date, time}`, set in the web task form) is the phone notification of an open task instead of the default time from its due (`core/reminders.ts`; zone of the trip day with that date, else home), moved by `shiftTripDates` like an `absolute` due; with reminders on, the phone pulls its planned trips by itself (`pullPlannedTrips` in `features/sync/sync-loop.ts`: background task, start, foreground at most every 10 min) and reschedules their notifications, so a reminder set on the web fires without opening that plan. `DocTask.deadline` (`tasks.deadline` date, „wykonać najpóźniej”) is a second date beside the due: `core/task-due.ts` `taskOverdue` (open task past its limit date `taskLimitDate`: the deadline when set, else the due date, relative ones resolved by `taskDueDate`) marks it red on the web list and the phone and as overdue in „Gotowość”; also moved by `shiftTripDates`. The web top bar (`Shell` → `components/task-alerts-server.tsx`) counts open tasks over all my planned trips (no drafts, postponed or past): overdue and due within 30 days (`taskDates`, `taskUrgency`), from light row queries (`lib/task-alerts.ts`, not `pull_changes`), today from the browser; a click lists trips with links to their „Zadania”. The phone has its own card on Start (`features/home/task-alerts.tsx` in `StatsCard`), open tasks of all my planned trips read straight from the phone database rows, so it works offline: collapsed it is three counts — overdue, within a week and all — and a tap on one opens that group’s five nearest tasks (date = `taskLimitDate` or the own reminder, whichever is first), so a reminder notification has its task on the screen until it is checked off. A row has a big checkbox (`setTaskStatus`) and opens the task window: what the phone may change is the status and the reminder date (`updateTask` in `packages/sync/src/outbox.ts` sends any task columns through the outbox, and `supabaseRemote` updates exactly those; the reminder is for the owner and editor, since `guard_viewer_task` lets a viewer change only the status), then `scheduleTripReminders` runs again; „Zadania wyjazdu” opens `/plan?tab=tasks` of that trip (`PLAN_TABS`, `Plan` prop `tab`). Calendar export: `/trips/[id]/calendar` (`core/calendar.ts`, ICS in UTC, UID per item ref). Climate for terms beyond the 16-day forecast (`core/climate.ts`: Open-Meteo archive ERA5, same calendar days in the last 10 years, one request per year from the browser; day length from `sunTimes`; place from the plan like the forecast, else the brief's first place via the Open-Meteo geocoder, `lib/climate-place.ts`), shown in „Zmień termin”, the date poll's best terms and the brief wizard (`components/climate-hint.tsx`); credit Open-Meteo CC BY, Copernicus, GeoNames. Budget vs spending per day (`core/budget-pace.ts`: day plan = lines pinned to the day's items + equal share of the rest; paid lines excluded) and weather go/no-go (`core/weather-alerts.ts`: bad forecast within 2 days + outdoor items; 19:00 reminder 2 days before). GPX tracks: the browser parses and simplifies the file (`core/gpx.ts`, ≤1500 points, DIN 33466 time) and `saveTrack` (`app/track-actions.ts`) at once stores the line in `tracks.geojson` (`DocTrack.geojson`) and replaces the item's km/time/ascent (`setItemRoute`, `user_locked`); `dayMap` draws it, phone `features/plan/track-card.tsx` shows position on the track offline. Profile and difficulty from the stored line: `core/track-profile.ts` `itemTrackWalk` (elevation profile; sections between summits and valleys with DIN 33466 time, scaled to the item's planned time by `planPace`; `trackDaylight`: finish vs sunset at the track start, the latest turnaround point that still gets back to the start before sunset, and from which km the finish is closer than going back), start time from the engine for the variants chosen in the plan view; web `components/track-profile.tsx` (SVG chart), phone `features/plan/track-profile.tsx` (bars, offline). Water, huts and emergency exits along the track: one Overpass query on click (`findTrackPois`, `app/track-actions.ts`; `planner/src/track-osm.ts`: `around` the simplified line inside its bbox, same FOSSGIS terms and `CONTACT_EMAIL` as transit lines), classified, placed by km and thinned in `core/track-pois.ts`, stored in `tracks.pois` (`DocTrack.pois`) so the phone has them offline; OSM credit with „zgłoś błąd” under the list. The lodging booking form sets the booking's place (name + coordinates or map link, `core/booking-place.ts`), which `dayLodging` prefers over `days.baseRef`. Foot routes from an external map: `core/item-route.ts` `setItemRoute` + `saveItemRoute` (link in `tracks.url`, typed km/time/ascent; the time goes into the item and drives the schedule, `user_locked` keeps „Przelicz przejazdy” off). Car legs get a plain Google Maps directions link (`drivingRouteUrl`, no API, nothing stored), replaced by an own `leg.routeUrl`; „Przelicz trasę” routes through that link's own via points (short link resolved by one HEAD reading only `Location`, `planner/src/google-link.ts`; coordinates parsed by `core/google-route.ts`; ORS draws the road, nothing from Google is stored, `docs/USLUGI.md` §3(c)); „Jedź przez” in the item editor (`leg.via`, up to 9 typed coordinates or map links, `parseViaPoints`, no new places) takes precedence over the link's via points, is used by `routeLegs` for every reroute and goes into `drivingRouteUrl` as `waypoints` — a Google link with only start and end does not fix the road; the web item editor sets from/to (`setLegRoute`, `components/item-leg.tsx`) and a change reroutes that item (`routeItem`; an end without coordinates is looked up by name, `locateLegEnds`, never guessed from neighbours). Public transport items (`isTransitItem`) get a Google Maps transit link the same way (`transitRouteUrl`, missing ends from neighbouring items via `legEnds`), and the web item card has „Przejazd komunikacją”: a connection pasted by the user (Google Maps, Jakdojade, operator site) → Gemini (`planner/src/transit.ts`) → per-field preview (`core/transit-info.ts` `transitDraftRows`, `applyTransitDraft`: segments also set `leg.line` and the mode, the time goes where the engine reads it, `leg.departures` holds pasted departure times). Lines show in plan rows and print (`transitLines`), details on the web card and phone details (`transitDetails`). Saving pasted segments (or „Narysuj na mapie”, `drawTransit`) also draws the line on the day map from OpenStreetMap: Overpass relations of those line numbers around the trip (`planner/src/transit-osm.ts`, `OVERPASS_URL`), cut between the named stops (`core/transit-shape.ts` `transitShape`, `applyTransitShape`), stored in `leg.geometry`; walks and unknown lines stay straight. FOSSGIS terms require `CONTACT_EMAIL` (shown in „Pomoc”; without it nothing is fetched), an identifying User-Agent and the OSM + „zgłoś błąd” credit on the map (`docs/USLUGI.md` Overpass). Never fetch transit results from Google (Routes API, Grounding): its terms forbid storing them (`docs/USLUGI.md` §3). Foot items without a saved link get a computed mapy.com link (`footRouteUrl`, documented `fnc/v1/route` address, the GPX line's waypoints when there is one; nothing stored), also as „Zaplanuj na mapy.com”. A GPX upload fills a missing from/to (`core/track-ends.ts` `setTrackEnds`: name „Trasa z A do B” from the mapy.com export, then a place right next to the end, otherwise a new place with the end's coordinates; a set end stays and only warns when far). Never fetch those numbers from the Mapy.com API: its terms forbid storing results (`docs/USLUGI.md` §5). „Co nowego od ostatniej wizyty”: RPC `trip_news` (others' `activity_log` entries since `trip_members.seen_changes_at`; `touch_trip` moves it to the end of the previous visit after a >1 h gap, `mark_changes_seen` = „Przejrzane”), summarized by `packages/sync/src/news.ts`; card on `/trips/[id]`, banner above the phone trip tabs. „Gotowość do wyjazdu” on the same page until the trip ends: `core/trip-readiness.ts` (bookings to book/pay/without vault document, nights without lodging, undecided choices, open tasks, points off the map) + people without account/phone. Traveler start/end (`travelers.start_place_id`, `end_place_id`; typed name matches a trip place or creates one in `transportFields`, `app/actions.ts`) feed „Wspólny transport” on the people page (`core/traveler-transport.ts`); they count as place usage and are hidden from the public link. The link gets only the number of tentative people (`public_trip.tentative`), never who. Per-traveler invite: `create_invite(..., p_traveler)` (single-use; `accept_invite` links the account to that traveler), „Zaproś” with a ready message on `/trips/[id]/people` (`FRIENDS_APK_URL` env = EAS install page, optional). People who already have an account from the owner's other trips are added without a link: „Dodaj z moich wyjazdów” after „Edytuj” (`components/known-accounts.tsx`, RPCs `known_accounts` = members of trips I own, never the whole user base, and `add_known_member` = editor/viewer + optional traveler; `addKnownMember` in `app/share-actions.ts` sends „Masz dostęp do wyjazdu” through the same SMTP when configured, `accessGrantedMessage`). „Wyślij e-mailem” there (`emailTravelerInvite`, `lib/mail.ts`) goes through SMTP from server env `SMTP_HOST/PORT/USER/PASS`, `MAIL_FROM`, also needed on Vercel; without them only copying is offered. Supabase Auth SMTP cannot be reused for own messages. Formalities on the same page: only the expiry dates of passport and ID (`travelers.passport_until`, `id_card_until`, never numbers; hidden from the public link, do not move with a reschedule; they follow the account: triggers in `*_shared_id_documents.sql` fill the EMPTY fields of the same `user_id` in other trips and give a newly linked traveler the missing dates, never overwriting typed ones); `core/travel-documents.ts` `documentWarnings` (expired, expires before the person's return, passport valid < 6 months after return) feed „Dokumenty tożsamości” in readiness; „Formalności” (`components/formalities.tsx`, `app/formality-actions.ts`) adds EKUZ, insurance, international driving permit and Odyseusz as ordinary tasks with a gov.pl service link and a due date before the trip (`formalityTasks`, no duplicates by title; nothing fetched from gov.pl). Traveler uncertainty and partial attendance on the same page: `travelers.tentative`, `from_date`/`to_date` (`core/traveler-presence.ts`; no dates = whole trip, moved by `shiftTripDates`), `notes`; hidden from the public link, no effect on costs or schedule. Souvenir: `/trips/[id]/memories` (`core/trip-memories.ts` stats and route refs, then a top-down timeline from `core/memory-timeline.ts` `memoryTimeline`: it opens with the outbound map and closes with the return map (`tripApproaches`, the same legs as the show's „Dojazd”/„Powrót”, drawn whole incl. flights; skipped items left out), per day a map without those legs (`components/memory-day-map.tsx` mounts MapLibre only near the screen, WebGL context limit), key points (`must`, a guide or a journal photo; treks — GPX track, `hike` leg, activity with km/ascent — always, with a square map of just that route fitted to the line (`PlanMap fitLines`) and, for a GPX track with heights, an elevation profile `components/walk-profile.tsx` from `profileSketch`, once per track) with the guide's first sentences (`shortText`), its Commons photo and credits, other points in one line each, journal entries under their item or between points by time, entries without a day at the end; `Settlement`, printable with SVG route traces); past trips sit in a collapsed „Archiwum” on both the web list and phone Wyjazdy, AI drafts (title prefix `Szkic AI: `, `isDraft`) in a collapsed „Szkice” at the very bottom. Renaming a trip: pencil next to the title on `/trips/[id]` (`components/trip-title.tsx`, `renameTrip` in `app/actions.ts`); drafts are linked to their plan by title, so a draft keeps its `Szkic AI: ` prefix and renaming a plan renames its drafts too. Postponed trips (`trips.status = 'postponed'`, `core/trip-status.ts`, set on the web trip page or in the new-trip form): own „Odłożone” section regardless of date, dates only tentative, no countdown, readiness or phone reminders. Rescheduling (web only): `core/trip-reschedule.ts` `shiftTripDates` decides what moves (days, unbought bookings, open absolute task dues, dated `decideBy`) and what stays as fact (bought bookings etc., listed in the preview with new engine warnings); `packages/sync/src/reschedule.ts` → RPC `reschedule_trip` writes it in one transaction, guarded by `sync_version`. - `packages/core/src/engine/`: the schedule engine (§7) — `scheduleDay`, `proposeCuts`, `checkCarKmLimit`, `priceForGroup`, sun/moon, zoned time via `Intl` (no date libs). Computes on UTC instants, displays local time. „Trekking”, „pieszo”, „transport publiczny” and „taksówka / transfer” in the kind lists are `transport` with `leg.mode` (`hike`/`walk`, `PUBLIC_MODES`, `HIRED_MODES` = `taxi`/`hired_driver`, routed on roads like a car), not separate kinds (`core/item-kind.ts`); „samolot” (`flight`) is offered under „transport publiczny” but is not transit (`publicMode`/`isTransitItem` exclude it: no transit link, paste or OSM line). Moving an item (`moveWithinDay`, `moveToDay`, `dropItem`) clears a time that no longer fits its new position, unless it is `isFixed` or an exact booking time. Removing an item (`removeItemClosingGap`) moves the following timed items earlier by the freed time, down to the first such held time; an `exact` time without a booking moves too. `items.stopsMin` (stops/breaks, web and phone item editors) lengthens the item on top of its duration or leg time. `day.dayEnd` only warns (`after_day_end`) and counts toward slack; the web plan edits it per day (`setDayEnd`, „Planowany koniec dnia”). `day.dayStart` (AI drafts set it on every day) is the earliest start for items without a held time; a held first time (`exact`, `by`, `isFixed`) earlier than it starts the day earlier instead of being pushed to it; edited as „Planowany początek dnia” (`setDayStart`). Free time of 15 min or more between items (before a held time, after the end of everything running so far incl. block children) shows as a „wolne …” line in the web and phone plan (`core/day-gaps.ts` `dayGaps`, sorted with the sun marks). The phone plan shows the same numbers as the day map above its points: tapping a number or card selects the pin and scrolls there (name = details), and tapping a pin scrolls the plan back to its first point. Plan times are "not earlier than"; `relative` + `from: previous` counts from the START of the previous item. `precision: 'by'` („dokładnie do”, e.g. a drive to the airport by 11:00) stores only `end`: the engine starts the item that long before (duration + route stops), the day's start counts back from it like from a first stated time, and arriving later is a `late` warning; the web editor offers it, and „dokładnie” with only „Do” saves as `by`. A child (`parentRef`) of a `transport` item is a stop on the route (`core/route-stops.ts`): it lengthens the parent (drive + `stopsMin` + stops), shows only its duration and is left out of „now/next” and reminders; children of other items stay parallel blocks. A transport outside the counted day (another variant, skipped) is not a parent: its child runs as an ordinary point. A point common to variants can be a stop in each: `parentRef` is the first transport, `routeParentRefs` the others (`itemsForDay` resolves the one counted), and „↳ postój w trasie” / „wyjmij z trasy” (`setRouteStop` with the viewed variant's options) change only the viewed variant. ## Conventions

- New files use LF (`.gitattributes` enforces `eol=lf`); never rewrite an existing file's line endings.
- Web actions are never underlined text: `btn-mini` (edytuj, zmień, also inside a sentence), `btn-mini btn-mini-danger` (usuń, odrzuć), `btn-secondary btn-sm` (Anuluj, + Dodaj…), `btn-primary btn-sm` (a form's Zapisz / Zastosuj). Going to another app page or downloading a file is a button too: `btn-secondary btn-sm` on its own, `btn-mini` inside a sentence or a list — also names that lead to an app page (points „w pakiecie”/„w planie”, contacts, „Korzystają”, readiness and news lines): `btn-mini` each, in a `flex flex-wrap gap-1` row, no commas. An address pasted into plain text (`LinkedText`) is a `btn-web` pill with `GlobeIcon` and the site name. Underline only for other external links, licences, and place names inside guide prose; plan row titles keep hover-underline. Function buttons and page-change buttons look different: an `<a>`/`<Link>` with `btn-mini`/`btn-secondary` renders as a yellow pill (`--nav-*` in `globals.css`, like `back-link`; `btn-primary` stays orange but rounded), a `<button>` stays filled and rectangular; so navigation is always a link, never `router.push` from a button, and a file download is an `<a download>` (styled as a function). Phone: `Button small`, `danger` for removal.
- Every web page has the same content width (`Shell`, `max-w-6xl`, the width of the plan with its map and of the film); don't give a page its own width.
- Web screen building blocks (`globals.css`, don't restyle them ad hoc): page heading = `PageHeader` (`components/page-header.tsx`: back, title, actions such as `EditToggle` on the right, intro); section = `card p-4` with `card-title` as its first child; frame inside a card = `panel`, a draft waiting for acceptance (AI, text read from a paste) = `panel-ai`; on/off filters and option choices = `toggle-chip` with `aria-pressed`; messages = `msg-error` / `msg-ok` (light and dark colours); dialogs = `<dialog className="card dialog">` with `DialogTitle` (✕ in the title bar; dialogs without a form also close on a backdrop click). Checkboxes and radios take the sea colour from `accent-color`.
- Web edit mode is one for all trip pages: session cookie `tryb_edycji` (`lib/edit-cookie.ts`), read by `editMode()` (`lib/edit-mode.ts`), switched by `EditToggle` („Edytuj” / „Zakończ edycję”). Never put the mode in the URL (`?edit=1`).
- Mobile is Android-only: don't add `*.web.tsx` variants.
- Distribution follows FormaSync: EAS channels `preview` (own phone) / `friends`, OTA with `runtimeVersion: appVersion` — bump `version` only together with a new APK (the APK version is `version` in `apps/mobile/app.json`; keep `package.json` equal). Current native set = APK 0.4.0 (0.2.0 added `expo-speech`, `expo-image-picker`; 0.3.0 `expo-brightness`; 0.4.0 adds `expo-network`, `expo-background-task` and the `SCHEDULE_EXACT_ALARM` permission: `features/sync/sync-loop.ts` sends the outbox and photos on network return and in a background task that also moves the reminder window, `requestExactAlarms` in `features/trip/reminders.ts`); code importing a module outside the installed APK crashes on use, so a new native module always means version bump + `eas build` for both profiles before any OTA that uses it. Friends' install/update flow: `docs/ZNAJOMI.md`.
