# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ExpeditionPlan: AI trip planner. Web **Planner Hub** (`apps/web`, Next.js) for planning, Android app **Expedition Planner** (`apps/mobile`, Expo; called „Pocket Guide” in the spec) for the trip itself, offline-first. Backend: Supabase (Postgres + RLS + Realtime + Storage), web on Vercel. Built by one developer on the experience of FormaSync (`D:\AI\Kardio`).

Read before larger work:
- `SPECYFIKACJA.md` — the spec. §5 is the data model, §7 the schedule/constraint engine, §4 the AI pipeline, §0.2 why the model looks the way it does (it was derived from the user's real plans in `examples/`).
- `PLAN_ETAPOWY.md` — stages (Etap 0 → PoC-0…5 → MVP-1…4 → v1.0). Each stage has an acceptance criterion; work toward it.
- `docs/USLUGI.md` — verified terms/limits of external services. Don't introduce a service it marks NIE (Google Places, MapTiler offline, tile.openstreetmap.org bulk).

All other docs (everything except this file, which is mixed), UI strings and code comments are in **Polish**; identifiers in English.

## Architecture rules

- **Domain logic lives in `packages/core`** and must run identically in the browser, on the phone (offline) and in Supabase Edge Functions (Deno). Keep it pure TS: no Node/Expo/Next imports outside tests.
- Packages are consumed as **TypeScript source** (`main: src/index.ts`), with **explicit `.ts` extensions in relative imports** — required by Deno. `allowImportingTsExtensions` is on everywhere; Next transpiles them via `transpilePackages`.
- **Zod schemas are the single source of truth** for form input, AI output, and `jsonb` columns. jsonb content is camelCase (Zod); table columns are snake_case.
- **Shared labels, formatting, errors:** labels of schema values live in `packages/core/src/labels.ts` (`MEMBER_ROLE` — `owner` shows as „organizator”, `CONTACT_ROLE`, `ITEM_KIND`, `BOOKING_KIND`, `PRICE_BASIS`, `BOOKING_STATUS`, `PAY_WHEN`, `PAY_METHOD`, `BUDGET_LINE_STATUS`, `NOTE_TOPIC`, `SLACK_LABEL`); don't redefine them in the apps. Formatting is in `packages/core/src/format.ts` (`plural`, `pluralForm`, `formatKm`, `dayLabel`, `dayLabelShort`, `dayChip`, `dayMonth`, `shortDate`, `capitalized`) plus `formatMinutes`, `formatMoneyRange`, `moneyToInput`, `fxLine`. A link meant for a human is `HttpUrl` (`schemas/common.ts`, http(s) only). Database errors shown to the user go through `dbErrorMessage` / `dbLoadError` (`packages/sync/src/remote.ts`); web actions load the trip with `pullTrip` and report schema errors with `validationError` (`apps/web/src/lib/trip-snapshot.ts`); `lockedRefs` (`packages/sync/src/document.ts`) lists the refs of `user_locked` items. On the Miejsca and Opisy miejsc pages changes sit behind „Edytuj” (`EditToggle`), as on Posiłki. Deleting a vault file from the bucket is a hard delete on purpose: the document is sensitive (`apps/web/src/components/vault.tsx`); journal files stay.
- Time in plans = **local date/time + IANA zone** (`LocalDateTime` + `TimeZone`), never UTC instants. Real events (expenses, delays) use timestamptz. Money = integer minor units + ISO currency; plan prices use the `Price` schema (ranges, "from", age tiers).
- `packages/planner`: the „Zaplanuj z AI” chain (`planTrip`: stage 1 → day facts → stage 2 chunks → pins → place grounding → ORS travel times when `route` is given), pure TS with injected AI client, place lookup (`geoapifyLookup` in the app, cached Nominatim/Photon in tools) and holidays. Used by the web server action `planWithAi` (Gemini, D8) and by `tools/plan-ai`. The result is a NEW trip „Szkic AI: …” via `import_trip`; the user moves points into the real plan on `/trips/[id]/compare?draft=…` (`packages/core/src/plan-merge.ts` + `saveMergeEdit`; copied items are `source: 'ai'`, not `user_locked`). Server keys `GEMINI_API_KEY`, `GEOAPIFY_API_KEY`, `OPENROUTESERVICE_API_KEY` reach `apps/web/.env.local` through `scripts/sync-env.mjs` (no `NEXT_PUBLIC_` prefix → never in the browser).
- `packages/ai`: one client (`createAiClient`) over Claude/Gemini/OpenAI; keys come from config/env (server-side only — never in the browser or APK). Use `askStructured(client, schema, prompt)` for anything that becomes data: it validates with Zod and gets exactly one repair attempt. Model names are never guessed — `listModels()` is the source. With `failover` (the web's Gemini clients) a busy model (503/529/429) gets one retry, then cheap stand-ins from that list (`fallbackModels`: newest stable Flash-Lite, then Flash, never Pro).
- AI produces **drafts and patches, never silent overwrites**; user-edited items are `user_locked`.
- **Propozycje AI** (`/trips/[id]/compare?review=1`, tile on the trip page, card on the compare chooser): `planner/src/review.ts` `reviewPlan` sends the plan with code facts (engine times/warnings, straight-line km from the previous mapped point and `transportBefore`, places off the map, short descriptions) → `PlanReview` = independent suggestions, each a `PatchOp[]` (the `/tune` ops plus `set_leg` and `set_place`; `set_place` only sets `searchName`, Geoapify places it on apply, private places are refused via `skipReason`). Stored in `ai_runs` (stage `review`, `StoredReview` with `applied`/`dismissed`). The page compares the plan with the same plan after all pending patches (same refs, exact new/changed/removed marks, `lib/review-view.ts`); apply/dismiss one or the selected (`app/review-actions.ts`). Saving after any AI patch goes through `lib/patch-save.ts` `savePatchedPlan` (grounding, `saveMergeEdit`, changed places via `saveElements`), shared with `/tune`.
- `packages/sync` (PoC-4): phone ↔ Supabase sync. Every write in a trip bumps `trips.sync_version` and stamps the row's `row_version` (trigger, serialized by the trip row lock); clients pull `row_version > last` via the `pull_changes` RPC (one snapshot). Phone writes (`schedule_events` append-only, `expenses`, `expense_splits`, `settlements`, `packing_checks`, `journal_entries` — `OutboxTable`) go through a SQLite outbox: local row + outbox entry in one transaction, idempotent upsert with client UUIDv7. No hard deletes — `deleted_at`. `LocalDb` is a sync interface (expo-sqlite in the app, `node:sqlite` in tests); the phone keeps server rows generically in one `rows (tbl, id, data)` table.
- **Schema (MVP-1)**: `supabase/migrations/*_mvp1_*.sql` = full §5 model (deviations in SPECYFIKACJA §5 „Odstępstwa w MVP-1”). Every `TripDocument` collection has a table with a `ref` column; common columns, version triggers, `activity_log` and RLS are added by loops in `mvp1_access.sql` — a new trip table goes into those arrays and into `synced_tables()`. `packages/sync/src/document.ts` (`SPECS`) is the only TripDocument ↔ rows mapping; a new document field needs a column there too (round-trip test over the 5 fixtures guards it). Whole documents are written via the `import_trip` RPC (one transaction, deferred FKs). Invites: `create_invite` / `accept_invite` (token hash only). Creating trips requires `app_metadata.trip_creator` (set only with the service key; `can_create_trips()` in RLS) — other accounts only see trips they were invited to; web AI/Geoapify/ORS actions additionally need the e-mail in `AI_ALLOWED_EMAILS`. Single-element writes outside the day plan (AI drafts stage 4/5, logistics editor) go through `saveElements` in `packages/sync/src/plan-save.ts`. After a migration: `npm run gen --workspace packages/db` (types), `npm run test:db` (pgTAP permission matrix).
- **Trip-time data outside `TripDocument`** (rows in `CachedTrip.live`, written via outbox): expenses + splits + settlements (`settle` in core: who owes whom, children to guardian, households), packing checks (shopping list = packing items in category `zakupy`, `core/meals.ts`; `items.self_cooked` marks meals cooked by the group), journal (`journal_entries`, photos in private bucket `journal`, phone queue in `features/trip/journal-photos.ts`). Receipt from a photo: phone `lib/web-api.ts` → web `POST /api/receipt` (Bearer session token, `AI_ALLOWED_EMAILS`, Gemini via `planner/src/receipt.ts`) → draft that fills the expense form. Calendar export: `/trips/[id]/calendar` (`core/calendar.ts`, ICS in UTC, UID per item ref). Climate for terms beyond the 16-day forecast (`core/climate.ts`: Open-Meteo archive ERA5, same calendar days in the last 10 years, one request per year from the browser; day length from `sunTimes`; place from the plan like the forecast, else the brief's first place via the Open-Meteo geocoder, `lib/climate-place.ts`), shown in „Zmień termin”, the date poll's best terms and the brief wizard (`components/climate-hint.tsx`); credit Open-Meteo CC BY, Copernicus, GeoNames. Budget vs spending per day (`core/budget-pace.ts`: day plan = lines pinned to the day's items + equal share of the rest; paid lines excluded) and weather go/no-go (`core/weather-alerts.ts`: bad forecast within 2 days + outdoor items; 19:00 reminder 2 days before). GPX tracks: the browser parses and simplifies the file (`core/gpx.ts`, ≤1500 points, DIN 33466 time) and `saveTrack` (`app/track-actions.ts`) at once stores the line in `tracks.geojson` (`DocTrack.geojson`) and replaces the item's km/time/ascent (`setItemRoute`, `user_locked`); `dayMap` draws it, phone `features/plan/track-card.tsx` shows position on the track offline. Profile and difficulty from the stored line: `core/track-profile.ts` `itemTrackWalk` (elevation profile; sections between summits and valleys with DIN 33466 time, scaled to the item's planned time by `planPace`; `trackDaylight`: finish vs sunset at the track start, the latest turnaround point that still gets back to the start before sunset, and from which km the finish is closer than going back), start time from the engine for the variants chosen in the plan view; web `components/track-profile.tsx` (SVG chart), phone `features/plan/track-profile.tsx` (bars, offline). Water, huts and emergency exits along the track: one Overpass query on click (`findTrackPois`, `app/track-actions.ts`; `planner/src/track-osm.ts`: `around` the simplified line inside its bbox, same FOSSGIS terms and `CONTACT_EMAIL` as transit lines), classified, placed by km and thinned in `core/track-pois.ts`, stored in `tracks.pois` (`DocTrack.pois`) so the phone has them offline; OSM credit with „zgłoś błąd” under the list. The lodging booking form sets the booking's place (name + coordinates or map link, `core/booking-place.ts`), which `dayLodging` prefers over `days.baseRef`. Foot routes from an external map: `core/item-route.ts` `setItemRoute` + `saveItemRoute` (link in `tracks.url`, typed km/time/ascent; the time goes into the item and drives the schedule, `user_locked` keeps „Przelicz przejazdy” off). Car legs get a plain Google Maps directions link (`drivingRouteUrl`, no API, nothing stored), replaced by an own `leg.routeUrl`; „Przelicz trasę” routes through that link's own via points (short link resolved by one HEAD reading only `Location`, `planner/src/google-link.ts`; coordinates parsed by `core/google-route.ts`; ORS draws the road, nothing from Google is stored, `docs/USLUGI.md` §3(c)); the web item editor sets from/to (`setLegRoute`, `components/item-leg.tsx`) and a change reroutes that item (`routeItem`; an end without coordinates is looked up by name, `locateLegEnds`, never guessed from neighbours). Public transport items (`isTransitItem`) get a Google Maps transit link the same way (`transitRouteUrl`, missing ends from neighbouring items via `legEnds`), and the web item card has „Przejazd komunikacją”: a connection pasted by the user (Google Maps, Jakdojade, operator site) → Gemini (`planner/src/transit.ts`) → per-field preview (`core/transit-info.ts` `transitDraftRows`, `applyTransitDraft`: segments also set `leg.line` and the mode, the time goes where the engine reads it, `leg.departures` holds pasted departure times). Lines show in plan rows and print (`transitLines`), details on the web card and phone details (`transitDetails`). Saving pasted segments (or „Narysuj na mapie”, `drawTransit`) also draws the line on the day map from OpenStreetMap: Overpass relations of those line numbers around the trip (`planner/src/transit-osm.ts`, `OVERPASS_URL`), cut between the named stops (`core/transit-shape.ts` `transitShape`, `applyTransitShape`), stored in `leg.geometry`; walks and unknown lines stay straight. FOSSGIS terms require `CONTACT_EMAIL` (shown in „Pomoc”; without it nothing is fetched), an identifying User-Agent and the OSM + „zgłoś błąd” credit on the map (`docs/USLUGI.md` Overpass). Never fetch transit results from Google (Routes API, Grounding): its terms forbid storing them (`docs/USLUGI.md` §3). Foot items without a saved link get a computed mapy.com link (`footRouteUrl`, documented `fnc/v1/route` address, the GPX line's waypoints when there is one; nothing stored), also as „Zaplanuj na mapy.com”. A GPX upload fills a missing from/to (`core/track-ends.ts` `setTrackEnds`: name „Trasa z A do B” from the mapy.com export, then a place right next to the end, otherwise a new place with the end's coordinates; a set end stays and only warns when far). Never fetch those numbers from the Mapy.com API: its terms forbid storing results (`docs/USLUGI.md` §5). „Co nowego od ostatniej wizyty”: RPC `trip_news` (others' `activity_log` entries since `trip_members.seen_changes_at`; `touch_trip` moves it to the end of the previous visit after a >1 h gap, `mark_changes_seen` = „Przejrzane”), summarized by `packages/sync/src/news.ts`; card on `/trips/[id]`, banner above the phone trip tabs. „Gotowość do wyjazdu” on the same page until the trip ends: `core/trip-readiness.ts` (bookings to book/pay/without vault document, nights without lodging, undecided choices, open tasks, points off the map) + people without account/phone. Traveler start/end (`travelers.start_place_id`, `end_place_id`; typed name matches a trip place or creates one in `transportFields`, `app/actions.ts`) feed „Wspólny transport” on the people page (`core/traveler-transport.ts`); they count as place usage and are hidden from the public link. The link gets only the number of tentative people (`public_trip.tentative`), never who. Per-traveler invite: `create_invite(..., p_traveler)` (single-use; `accept_invite` links the account to that traveler), „Zaproś” with a ready message on `/trips/[id]/people` (`FRIENDS_APK_URL` env = EAS install page, optional). „Wyślij e-mailem” there (`emailTravelerInvite`, `lib/mail.ts`) goes through SMTP from server env `SMTP_HOST/PORT/USER/PASS`, `MAIL_FROM`, also needed on Vercel; without them only copying is offered. Supabase Auth SMTP cannot be reused for own messages. Formalities on the same page: only the expiry dates of passport and ID (`travelers.passport_until`, `id_card_until`, never numbers; hidden from the public link, do not move with a reschedule); `core/travel-documents.ts` `documentWarnings` (expired, expires before the person's return, passport valid < 6 months after return) feed „Dokumenty tożsamości” in readiness; „Formalności” (`components/formalities.tsx`, `app/formality-actions.ts`) adds EKUZ, insurance, international driving permit and Odyseusz as ordinary tasks with a gov.pl service link and a due date before the trip (`formalityTasks`, no duplicates by title; nothing fetched from gov.pl). Traveler uncertainty and partial attendance on the same page: `travelers.tentative`, `from_date`/`to_date` (`core/traveler-presence.ts`; no dates = whole trip, moved by `shiftTripDates`), `notes`; hidden from the public link, no effect on costs or schedule. Souvenir: `/trips/[id]/memories` (`core/trip-memories.ts` stats and route refs, journal photos, `Settlement`, printable with an SVG route trace); past trips sit in a collapsed „Archiwum” on both the web list and phone Wyjazdy, AI drafts (title prefix `Szkic AI: `, `isDraft`) in a collapsed „Szkice” at the very bottom. Postponed trips (`trips.status = 'postponed'`, `core/trip-status.ts`, set on the web trip page or in the new-trip form): own „Odłożone” section regardless of date, dates only tentative, no countdown, readiness or phone reminders. Rescheduling (web only): `core/trip-reschedule.ts` `shiftTripDates` decides what moves (days, unbought bookings, open absolute task dues, dated `decideBy`) and what stays as fact (bought bookings etc., listed in the preview with new engine warnings); `packages/sync/src/reschedule.ts` → RPC `reschedule_trip` writes it in one transaction, guarded by `sync_version`. A new date field in `TripDocument` must be decided there. All places across my trips, without AI drafts: `/places` (`core/place-list.ts` `placesAcrossTrips`, one row per place name unless far apart; button on the trip list; `?miejsce=<ref>` selects a place on the trip's page; the plan itself is not edited there). Place memory between trips on the same page: table `place_memories` (outside `TripDocument`, no `trip_id`), one row per user and place with „warto / nie warto” and a note for the future, written only via RPC `set_place_memory(place, verdict, note)` (any member role; empty both = delete; author name from the trip's traveler); the same place across trips = `place_key(name)` (SQL twin of `plainName`) + coords within 1 km, RLS `can_see_place_memory` lets every member of a trip with such a place see it. Visit years are never stored: `placeVisitYears` from start dates of trips that already started, not postponed (`core/place-memory.ts`: `memoriesOf`, `memorySummary`, `visitLabel`; web `lib/places-across.ts` loads places + memories, `components/all-places-view.tsx`, `app/place-memory-actions.ts`). The same voting (`components/place-memory.tsx`, not behind „Edytuj”: it is a person's vote, not a plan change) sits under the map for the selected place on the trip's „Miejsca” page, with 👍/👎 counts in the place rows. „Zaplanuj z AI” gets it as context: `plannerMemory` (skips the trip being planned) → `PlannerDeps.memory` → `memorySection` in both stage prompts („[unikaj]” = more „nie warto” or already visited: only with a stated reason), and `withMemoryWarning` adds a trip warning to the draft when it still proposes such a place (`rememberedInPlan`). Places page: `/trips/[id]/places` (`core/place-list.ts` usage and unused removal, `app/place-actions.ts`; coordinates through `pinPlace`, shared by every item using the place; under the square map the selected place's guide, `core/guide.ts` `placeGuide`, new one via `describePlaceGuide`, whose optional `which` says which of the same-named places is meant and stays in `content.hint` of the place's guide). Merging duplicates: `mergePlaces` repoints every reference (a new field pointing at a place goes there, a test over the fixtures guards it), `mergePlace` also moves `audio_guides`; `similarPlaces` only suggests. Booking details (`core/booking-details.ts` `bookingDetails`: when, price, conditions, package items, contacts) feed the web „Rezerwacje” table and the phone booking sheet (`features/plan/booking-sheet.tsx`); a plan item leads to its booking (`itemBookingRef`: own, leg ticket, or the night's lodging), on the web as a link to the row anchor (`lib/booking-link.ts`), on the phone as „🎫 Rezerwacja”. Removing a cancelled booking (web): `core/booking-remove.ts` clears every reference to it; a new field pointing at a booking goes there (a test over the fixtures guards it).
- **Dla kogo pozycja budżetu i wydatek:** `DocBudgetLine.participantRefs` (`budget_lines.participant_ids`, brak = wszyscy, także dodani później; komplet osób zapisuje się jako brak). „Na osobę” mnoży tylko przez wybranych (`lineTravelers`, też w `budgetPace`), a pozycja łączna dzieli się tylko na nich. `budgetSummary` daje `perTraveler`, a `perPersonLowMinor` jest `null`, gdy osobom wypada co innego: wtedy web i telefon pokazują kwotę każdej osoby. Wydatki: `expense_splits` jak dotąd, wybór w portfelu na telefonie i przy wydatku na webie (`setExpenseSplits`, wspólne `expenseSplitRows`); same wydatki dodaje się tylko na telefonie.
- **Podział na auta:** `vehicles` jest w `TripDocument` (`DocVehicle`: kierowca, miejsca razem z kierowcą, `passengerRefs`); `vehicles.booking_id` zostaje bez pola. Web: sekcja „Podział na auta” na `/trips/[id]/people` (`components/car-split.tsx`, `app/vehicle-actions.ts`, wiersze zapisywane wprost jak uczestnicy). `core/vehicles.ts` `carPlan` liczy wolne miejsca, odbiór pasażerów z ich `start_place_id` innego niż start kierowcy, odwiezienie na koniec, osoby bez auta z podpowiedzią „dosadź” i jazdę w inne dni. Osoba siedzi w jednym aucie: zapis auta zabiera ją z innego. Paliwo i winiety: `DocBudgetLine.vehicleRef` (`budget_lines.vehicle_id`) dzieli pozycję na osoby auta (`lineTravelers` → `vehicleTravelers`), a `expenses.vehicle_id` (ustawiany przy wydatku na webie) dzieli wydatek bez własnego `expense_splits` na osoby auta w `settle` (web i telefon podają `vehicles` do `settleInputFromRows`). Usunięcie auta czyści te odwołania; uczestnika w aucie nie da się usunąć.
- **Waluta wyjazdu:** `trips.base_currency` zmienia się na „Rezerwacje i budżet” (`setTripCurrency`, `core/rates.ts` `rebaseRates`). Sumy, plan dzień po dniu i rozliczenie liczą się w niej, a kwoty pozycji i wydatków zostają w swoich walutach; kursy przechodzą przez kurs nowej waluty, a dawna dostaje własny. Kursy z telefonu są w pliku osobnym dla każdej waluty (`features/trip/live-rates.ts`).
- **Sprzęt:** `/trips/[id]/gear` i zakładka „Sprzęt” na telefonie (`features/trip/packing-view.tsx`) to `packing_items` poza kategorią `zakupy`. Osobiste pakuje każdy (`assigneeRef` = tylko ta osoba), przy wspólnych o tym, kto bierze, decydują wiersze `packing_carriers` z ilością (rzecz można dzielić; spoza `TripDocument`, w `CachedTrip.live`, outbox `setCarrying`, prawa jak `packing_checks`: za siebie i swoje dzieci, organizator i edytor za każdego). `quantity = 0` to „nie biorę”. `assigneeRef` przy wspólnej (plan, import) liczy się jako osoba biorąca całość, póki nie ma własnego wiersza (`core/gear.ts` `gearCarriers`); opcjonalne `weightG` to waga sztuki do „Kto ile niesie” (`gearLoads`). Braki (`gearGaps`) trafiają do „Gotowości do wyjazdu”.
- **Posiłki w wariantach:** strona „Posiłki” używa `mealList(doc, { allVariants: true })`: posiłki z niewybranych wariantów są na liście i mapie z nazwą wariantu, ale nie liczą się do porcji (`selfCookedTotals`), a kopie posiłku dla kolejnych knajp (`eatOutGroup`) zostają pod posiłkiem.
- **Posiłek przy punkcie:** `linkMeal` (`core/meals.ts`, wybór `MealLink` na „Posiłkach” i w edytorze planu) ustawia `parentRef` posiłku na punkt tego dnia. Posiłek stoi pod punktem, a jego godzina to `relative` od początku punktu (`from: previous` u podpunktu liczy się od rodzica). W odróżnieniu od innych podpunktów bloku posiłek kończący się później przesuwa następny punkt. Przy przejeździe to zwykły postój w trasie. - **Place guides (M8):** one `audio_guides` row per place (`content` jsonb = `GuideContent` in `core/guide.ts`). `guide_library` is a shared cache across trips keyed by article (`GuideLibrary` in `planner/src/wiki.ts`): a ready text is copied into the trip without AI, only for guides without hint/`which` whose article bears the place's name; „Odśwież” (`fresh`) makes a new version, other trips keep their copy. - `packages/core/src/engine/`: the schedule engine (§7) — `scheduleDay`, `proposeCuts`, `checkCarKmLimit`, `priceForGroup`, sun/moon, zoned time via `Intl` (no date libs). Computes on UTC instants, displays local time. „Trekking”, „pieszo” and „transport publiczny” in the kind lists are `transport` with `leg.mode` (`hike`/`walk`, `PUBLIC_MODES`), not separate kinds (`core/item-kind.ts`). Moving an item (`moveWithinDay`, `moveToDay`, `dropItem`) clears a time that no longer fits its new position, unless it is `isFixed` or an exact booking time. Removing an item (`removeItemClosingGap`) moves the following timed items earlier by the freed time, down to the first such held time; an `exact` time without a booking moves too. `items.stopsMin` (stops/breaks, web and phone item editors) lengthens the item on top of its duration or leg time. `day.dayEnd` only warns (`after_day_end`) and counts toward slack; the web plan edits it per day (`setDayEnd`, „Planowany koniec dnia”). The phone plan shows the same numbers as the day map above its points: tapping a number or card selects the pin and scrolls there (name = details), and tapping a pin scrolls the plan back to its first point. Plan times are "not earlier than"; `relative` + `from: previous` counts from the START of the previous item. A child (`parentRef`) of a `transport` item is a stop on the route (`core/route-stops.ts`): it lengthens the parent (drive + `stopsMin` + stops), shows only its duration and is left out of „now/next” and reminders; children of other items stay parallel blocks. A transport outside the counted day (another variant, skipped) is not a parent: its child runs as an ordinary point. A point common to variants can be a stop in each: `parentRef` is the first transport, `routeParentRefs` the others (`itemsForDay` resolves the one counted), and „↳ postój w trasie” / „wyjmij z trasy” (`setRouteStop` with the viewed variant's options) change only the viewed variant. A new way of clearing `parentRef` must clear these too (`dropRouteParent`). The `bramka PoC-5` test keeps all five fixture plans within ±15 min — keep it green.

## Reference data

`fixtures/plans/<slug>/brief.json` are the user's five real trips as `TripBrief`; `plan.json` is the full hand-checked `TripDocument` (gold standard for AI import) and `GAPS.md` lists what the schema could not hold. `packages/core/src/__tests__/fixtures.test.ts` validates them — a schema change that breaks them is a regression. ## Conventions

- New files use LF (`.gitattributes` enforces `eol=lf`); never rewrite an existing file's line endings.
- Web actions are never underlined text: `btn-mini` (edytuj, zmień, also inside a sentence), `btn-mini btn-mini-danger` (usuń), `btn-secondary btn-sm` (Anuluj, + Dodaj…). Going to another app page or downloading a file is a button too: `btn-secondary btn-sm` on its own, `btn-mini` inside a sentence or a list — also names that lead to an app page (points „w pakiecie”/„w planie”, contacts, „Korzystają”, readiness and news lines): `btn-mini` each, in a `flex flex-wrap gap-1` row, no commas. Underline only for external links, licences, and place names inside guide prose; plan row titles keep hover-underline. Function buttons and page-change buttons look different: an `<a>`/`<Link>` with `btn-mini`/`btn-secondary` renders as a yellow pill (`--nav-*` in `globals.css`, like `back-link`), a `<button>` stays filled; so navigation is always a link, never `router.push` from a button, and a file download is an `<a download>` (styled as a function). Phone: `Button small`, `danger` for removal.
- Web edit mode is one for all trip pages: session cookie `tryb_edycji` (`lib/edit-cookie.ts`), read by `editMode()` (`lib/edit-mode.ts`), switched by `EditToggle` („Edytuj” / „Zakończ edycję”). Never put the mode in the URL (`?edit=1`).
- Mobile is Android-only: don't add `*.web.tsx` variants.
- Distribution follows FormaSync: EAS channels `preview` (own phone) / `friends`, OTA with `runtimeVersion: appVersion` — bump `version` only together with a new APK (the APK version is `version` in `apps/mobile/app.json`; keep `package.json` equal). Current native set = APK 0.3.0 (0.2.0 added `expo-speech`, `expo-image-picker`; 0.3.0 adds `expo-brightness`); code importing a module outside the installed APK crashes on use, so a new native module always means version bump + `eas build` for both profiles before any OTA that uses it. Friends' install/update flow: `docs/ZNAJOMI.md`.
